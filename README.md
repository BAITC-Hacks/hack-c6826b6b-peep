# Career Quest

Кейс Halyk Bank / HackAlem AI. **Flutter Web + FastAPI + SQLite.**

Сотруднику нужен понятный путь от текущих навыков к карьерной цели. Текущий **этап 2** даёт основу этого пути: вход сотрудника и HR с серверной проверкой прав, профиль, историю активностей, сохранение цели и импорт дополнительных проверочных данных. Веб-интерфейс посвящён работе сотрудника и HR; технические сводки и статус запуска сервера в него не входят.

Рекомендации, AI-объяснения, выполнение активностей, расчётный прирост навыков и HR-аналитика — следующие этапы. Сейчас уровни навыков показывают последнюю оценку из данных, а не заработанный прогресс.

## Запуск одной командой

Требования: Python 3.11+ и Flutter 3.47.5 (Dart 3.13.4) в PATH. Разработка ведётся на Linux; команды предусмотрены для Linux и Windows, но запуск на Windows требует отдельной проверки.

```text
python run.py
```

На Linux при необходимости используйте `python3 run.py`, на Windows — `py run.py`. Скрипт создаёт `.venv`, устанавливает Python-зависимости, собирает Flutter Web и запускает приложение на **http://127.0.0.1:8000**. Первый запуск требует интернета для зависимостей и сборки. Остановка: Ctrl+C.

Повторный запуск без пересборки неизменённого интерфейса: `python run.py --skip-build`. Другой порт: `python run.py --port 8001`. Flutter и API обслуживаются с одного адреса. Swagger для разработки: http://127.0.0.1:8000/docs.

## Демонстрационные учётные записи

| Логин | Пароль | Доступ |
| --- | --- | --- |
| `employee.demo` | `Employee123!` | Собственный профиль, история, цель |
| `colleague.demo` | `Colleague123!` | Профиль второго сотрудника; проверка изоляции доступа |
| `hr.demo` | `Hr123!` | Каталог сотрудников, профили и импорт проверочных данных |

При первичном наполнении БД сотрудники привязываются к первым двум ID исходного набора в отсортированном порядке. HR не привязан к профилю сотрудника. Это локальные демонстрационные аккаунты, а не производственная авторизация или SSO. Импорт нового профиля не создаёт ему учётную запись; HR видит его в каталоге.

Права проверяются сервером при каждом защищённом запросе. Bearer-токен хранится в памяти приложения: после обновления страницы нужно войти снова. Чужой профиль и история недоступны сотруднику, даже если запросить их API напрямую.

Если в данных есть цель, она отображается в профиле. Если её нет, следующий грейд той же роли предлагается отдельно и становится целью только после явного сохранения. Для Lead следующий грейд не выдумывается.

Вход: `POST /api/auth/login`, текущая учётная запись: `GET /api/auth/me`, выход: `POST /api/auth/logout`. Собственный профиль: `GET /api/me/profile`; цель: `PUT /api/me/goal` и `DELETE /api/me/goal`. Удаление личной цели восстанавливает цель из текущего исходного профиля, а при её отсутствии — предложение следующего грейда. Профиль и история по ID доступны через `GET /api/employees/{id}` и `GET /api/employees/{id}/history` с той же проверкой прав.

## Подготовка исходных данных

Исходный синтетический стартовый кит включён в приватный репозиторий команды по указанию пользователя. После клонирования четыре файла данных и три описания уже находятся в `data/sample/`; отдельная передача архива напарнику не нужна. Для восстановления исходников из выданного ZIP при необходимости:

```text
python scripts/prepare_data.py "/path/to/career_quest_dataset.zip"
```

На Windows укажите собственный путь к ZIP. Скрипт переносит только четыре ожидаемых файла в `data/sample/`, не исполняет содержимое архива и не заменяет отличающиеся локальные файлы. Если БД ещё не наполнена и исходного набора нет, сначала подготовьте его и перезапустите сервер.

Каталог исходников можно задать через `CAREER_DATA_DIR`, путь к SQLite — через `CAREER_DB`. Примеры находятся в `.env.example`; `.env` автоматически не читается. В Git включён только исходный стартовый кит; дополнительные импортируемые файлы, локальная БД с аккаунтами/сессиями и секреты остаются локальными. Данные предназначены для работы команды в рамках хакатона; репозиторий остаётся приватным.

При первом запуске набор сохраняется в SQLite. В дальнейшем приложение читает текущие записи из БД: перезапуск не отменяет импорт или личную цель и не загружает исходные файлы поверх изменений. Для отдельной демонстрации с чистой базой задайте новый путь `CAREER_DB`.

## Импорт проверочных данных

Войдите как HR и откройте загрузку данных. Можно передать профили, историю или оба файла одним пакетом:

- **Профили:** JSON в исходной схеме — массив профилей или объект с массивом `employees` и необязательным исходным `meta`. Если передан `meta.as_of_date`, он должен совпадать с датой исходного набора.
- **История:** CSV с исходными именами столбцов, включая `record_id`, `employee_id` и `event_id`.
- Справочники навыков, ролей и мероприятий берутся из стартового кита. Импорт профилей и истории не добавляет новые определения справочников.

Сначала создаётся предпросмотр без изменения рабочих данных. Он показывает результат проверки и будущие изменения. Только отдельное подтверждение применяет пакет.

| Ситуация | Поведение |
| --- | --- |
| Новый ID | Добавление записи |
| Существующий ID и то же содержимое | Пропуск без дубликата |
| Существующий ID с отличающимся содержимым | По умолчанию отказ; для намеренного обновления выберите замену |
| Ошибка формата, повтор ID внутри файла или неверная ссылка | Отказ от всего пакета, рабочие данные сохранены |
| Новая история ссылается на новый профиль из того же пакета | Допустимо после проверки всех связей |
| Данные изменились после предпросмотра | Предпросмотр устарел; нужно создать новый |
| Предпросмотр уже применён | Повторное применение отклоняется |

API: `POST /api/hr/import/preview` принимает `multipart/form-data` с необязательными `employees_file` и `history_file` (нужен хотя бы один), а также `conflict_policy=reject` или `replace`. `POST /api/hr/import/commit` принимает JSON `{ "preview_id": "…" }` и после применения возвращает HTTP 201. Конфликт ID, устаревший или уже применённый предпросмотр возвращает HTTP 409. Для обоих запросов нужен токен HR.

Сохраняются отдельно неизменяемые исходные записи и текущие записи после импорта; личная цель отделена от исходного профиля. Политика замены обновляет текущую запись, сохраняя исходную и личную цель. Расчётный прирост навыков пока не выполняется. История сама по себе не меняет последнюю оценку навыков.

## Структура

```text
backend/                # API, права доступа, валидация и SQLite
frontend/lib/           # Flutter: вход, профиль, история и сценарий HR
scripts/prepare_data.py # Подготовка локального исходного набора
run.py                  # Общий запуск для Linux/Windows
requirements.txt        # Прямые Python-зависимости
requirements.lock       # Полный снимок Python-зависимостей
frontend/pubspec.lock
tests/                  # Проверки сервера и работы с данными
docs/05-roadmap.md       # Текущий объём и следующие этапы
```

## Разработка отдельно

Бэкенд на Linux:

```text
.venv/bin/python -m uvicorn backend.main:app --reload --port 8000
```

Бэкенд на Windows:

```text
.venv\Scripts\python.exe -m uvicorn backend.main:app --reload --port 8000
```

Фронтенд, из `frontend/`:

```text
flutter run -d web-server --web-hostname 127.0.0.1 --web-port 8080 --dart-define=API_BASE_URL=http://127.0.0.1:8000
```

Открыть http://127.0.0.1:8080. После изменения UI для общего сервера снова выполнить `python run.py`.

## Проверка этапа 2

Запуск тестов на Linux: `.venv/bin/python -m pytest`; на Windows: `.venv\Scripts\python.exe -m pytest`. В `frontend/` выполнить `flutter analyze`, `flutter test` и `flutter build web`.

Основная приёмка: новый профиль появляется после импорта без изменения кода; неверная ссылка отклоняет пакет целиком; повторный импорт не создаёт дубликаты; сотрудник не получает чужой профиль и историю; сохранённые данные переживают перезапуск. В интерфейсе дополнительно проверяются состояния загрузки, ошибки, выход и узкий экран.
