# Career Quest: согласованный результат и этапы

## Решение

Кейс 1 Career Quest, Halyk Bank / HackAlem AI. Веб-приложение связывает профиль сотрудника, историю и требования роли с 1–3 объяснимыми шагами развития. Сотрудник видит изменение прогресса после выполнения. HR получает срез дефицитов компетенций и участия. Это целевой результат, а не описание уже реализованного продукта.

Проблема по ТЗ: разрозненные HR-уведомления не объясняют связь активности с развитием. Гипотеза продукта: понятная связь с личной целью помогает осознанно выбирать и завершать обучение. Синтетический датасет не доказывает эффект на реальных сотрудниках; показатели завершения и явки нужно измерять в пилоте.

## Зафиксированный стек

- Flutter Web / Dart — единый веб-интерфейс, адаптивная компоновка.
- Python 3.11+ / FastAPI / Pydantic — API, проверка данных и бизнес-правила. Локально проверяется Python 3.14.
- SQLite — локальное хранение без отдельного сервера базы данных.
- HTTP/JSON, документирование через OpenAPI `/docs`.
- AI-адаптер на бэкенде — следующий этап; провайдер и модель ещё не выбраны. Ключи хранятся только на сервере.
- Flutter 3.47.5 / Dart 3.13.4 используются локально. Android APK — за границами текущего объёма; Linux/Windows runners сгенерированы, но не являются целевыми сборками.

## Этап 1 — сервер и две страницы (история подготовки)

- Локальный сервер, `GET /api/health`, `GET /api/dataset/summary`, Swagger.
- Чтение четырёх файлов, валидация типов, диапазонов, идентификаторов и связей. Исходники не меняются.
- SQLite хранит метаданные загрузки и ревизию среза, не вычисленный карьерный прогресс.
- Страница «Обзор»: связь с сервером и границы текущей версии.
- Страница «Данные»: реальные объёмы, дата среза, файлы и замечания качества.
- Загрузка, ошибка, повтор запроса, компоновка для узкого экрана.
- Одна команда запуска после установки Python/Flutter: `python run.py`.

Этот этап служил проверкой инфраструктуры. На этапе 2 технические страницы «Обзор»/«Данные», сведения о срезах и сообщение о запущенном FastAPI заменены пользовательскими экранами. Техническая диагностика остаётся задачей API и журналов. Запуск по умолчанию остаётся локальным, только через loopback.

## Этап 2 — доступ, профиль и загрузка проверочных данных (реализован)

- Демонстрационные учётные записи `employee.demo`, `colleague.demo` и `hr.demo`; сервер проверяет сессию и права каждого защищённого запроса. Токен хранится в памяти Flutter; обновление страницы требует повторного входа. Это локальная демонстрация, не SSO.
- Сотрудник видит собственный профиль, историю, последнюю оценку навыков и цель. Чужие профиль и история запрещены сервером. HR видит каталог, открывает профили и загружает проверочные данные.
- Цель сохраняется отдельно от исходного профиля. Если цель отсутствует, следующий грейд той же роли показан как предложение и требует явного сохранения. Для Lead следующего грейда нет. Сброс личной цели возвращает цель текущего исходного профиля либо предложение.
- SQLite содержит неизменяемые исходные записи и текущие профили/историю после импорта. Личная цель хранится отдельно. Перезапуск не отменяет изменения повторным наполнением из файлов.
- Значения последней оценки показываются отдельно от будущего расчётного прироста; на этом этапе история не изменяет навыки. Сводные дефициты, рекомендации и отметка выполнения пока не реализуются.
- Интерфейс: вход, рабочее пространство сотрудника и HR. Адаптивная навигация, понятные состояния загрузки, ошибки и пустой истории. Технические сведения о датасете и запуске сервера убраны из пользовательских экранов.

### Правила импорта

HR может загрузить JSON-профили и/или CSV-историю в исходной схеме, включая судейские файлы. JSON принимает массив профилей либо объект с `employees` и необязательным `meta`; переданный `meta.as_of_date` должен совпадать с датой исходного набора. Справочники навыков, ролей и мероприятий на этом этапе не расширяются.

1. `POST /api/hr/import/preview` проверяет файлы без изменения рабочих данных: типы, диапазоны, уникальность ID, ссылки и итоговое состояние набора. Профили и история одного пакета могут ссылаться друг на друга.
2. Новые ID добавляются. Полностью одинаковые записи пропускаются. Отличающиеся записи с существующим ID по умолчанию отклоняются с HTTP 409; политика `replace` разрешает явную замену текущих исходных значений. Личная цель и первоначальная запись сохраняются отдельно.
3. `POST /api/hr/import/commit` с `preview_id` применяет проверенный пакет одной транзакцией. Ошибка не меняет рабочие записи. Повторный импорт того же содержания не создаёт дубликатов.
4. Если состояние БД изменилось после предпросмотра или он уже был применён, подтверждение отклоняется с HTTP 409. HR создаёт новый предпросмотр.

Импортированный сотрудник появляется в каталоге HR без изменения кода. Новые демонстрационные логины при этом автоматически не создаются. Стартовые учётные записи привязываются к первым двум отсортированным employee ID только при первичном наполнении БД.

Приёмка: новый профиль загружается без изменения кода; неверная ссылка отклоняет весь пакет и не портит базу; сотрудник не читает чужие профиль и историю; повтор файла не создаёт дубликаты; конфликт, замена и устаревший предпросмотр обработаны явно; импорт и цель сохраняются после перезапуска. Отдельно проверяются браузерный вход/выход, сохранение цели, импорт и узкий экран. Результаты и ограничения проверки: [отчёт этапа 2](07-stage2-verification.md).

## Этап 3 — ядро рекомендаций и AI (ожидает отдельного указания)

- Расчёт дефицита относительно целевого грейда с особым учётом critical_skills.
- Учитывать историю завершений, пропусков, отказов, активностей в работе, роль/грейд, prerequisites, даты сессий и формат. Пропуски — сигнал для обсуждения предпочтений, а не характеристика человека.
- Уровни из последней оценки и расчётный прирост после неё показывать отдельно; gain/max_level не должны понижать уже более высокий навык.
- Обязательные мероприятия отделить от рекомендаций; не начислять за них игровые баллы.
- Отобрать 1–3 шага. Объяснение содержит проверяемые ссылки на факторы: дефицит, критичность, история, доступность и ожидаемый прирост.
- LLM работает с ограниченным контекстом и проверенными кандидатами. Структурированный ответ проверяет сервер: существующие event_id, отсутствие выдуманных навыков и эффектов. Разобрать правила использования данных до передачи внешнему сервису.
- Тайм-аут/ошибка модели: явно обозначенный многофакторный алгоритмический ответ, не имитация LLM.
- Отличие для демо: «Почему этот шаг, а не другой?» — сравнение обоснований, а не просто список курсов.

Приёмка: сценарий из ТЗ с низким Public Speaking, повторными пропусками и критичным System Design обрабатывается по нескольким факторам. Нельзя обещать повышение: показываем покрытие навыков. AI-ответ ≤10 секунд в измеренном сценарии.

## Этап 4 — выполнение и HR-аналитика (ожидает отдельного указания)

- Завершение активности в явно обозначенном деморежиме, сохранение истории, обновление навыков по правилам датасета.
- Защита от повторного прироста одной и той же записи, повторяемость EV_036, ограничения max_level и отсутствие двойного учёта после переоценки.
- Пересчёт рекомендаций и прогресса после завершения.
- HR: дефициты компетенций и признаки отсутствия участия с периодом и понятным знаменателем. Без публичного рейтинга сотрудников и необоснованного «прогноза увольнения».

Приёмка: выполнить действие → увидеть воспроизводимый прирост → перезапустить сервер → результат сохранён. Повторный запрос не увеличивает навыки второй раз.

## Этап 5 — последний час: проверка и защита (предстоит)

- Проверочные профили и граничные случаи; роли доступа; импорт; отказ LLM; пустая история; отсутствие подходящих мероприятий.
- Проверка веба на обеих машинах, отклик интерфейса ≤2 секунд в измеренных сценариях.
- Репетиция демо на 60–90 секунд: профиль → почему выбран шаг → выполнение → прогресс → HR.
- Инструкция запуска, ограничения, резервная запись реального демо.

При бюджете в 3 часа разработки этапы 2–4 нужно держать минимальными. Расширенная визуализация траекторий, награды, магазин, голос, календарь, SSO и APK откладываются.

## Выявленное расхождение данных

README набора разрешает повтор после completed только для EV_036. Фактическая история содержит также повторные completed для EV_001–EV_003 (комплаенс). Они сохраняются как исходные записи; правила расчёта прироста пока не применяются. До реализации расчётов принять и документировать трактовку: возможные повторные обязательные назначения не превращать в повторный карьерный прирост.

Дата среза набора — 2026-10-01; она используется вместо системной даты для будущих алгоритмов. Для self_paced поле date — дата зачисления, не окончания: точный момент прироста может быть неизвестен.

## Данные и границы

Использовать синтетический стартовый кит и проверочные файлы хакатона. Исходные и импортируемые JSON/CSV, SQLite и локальные секреты исключены из Git; стартовые файлы готовятся локальным скриптом. Ничего не публиковать. До подключения LLM проверить ограничения передачи стартового кита провайдеру. Сейчас внешних AI-вызовов нет.

Следующие этапы начинаются только по отдельному указанию пользователя.
