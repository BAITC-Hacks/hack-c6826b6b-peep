## Linux и Windows

Участники подтвердили разные ОС, предпочтений по стеку пока нет.

- Выбирать команды запуска, работающие на обеих ОС; при необходимости документировать отдельно Bash и PowerShell.
- Не использовать абсолютные пути одной машины в коде и конфигурации.
- Соблюдать регистр имен файлов и импортов: ошибка, незаметная на Windows, может сломать запуск на Linux.
- Версии среды согласовать после выбора стека, до установки зависимостей.
- Docker пока необязателен: наличие работающего Docker на Windows не подтверждено.
- Проверить запуск на обеих машинах до наполнения приложения функциями; отдельно выбрать машину для демонстрации.

## Совместная разработка

- Один репозиторий, отдельные ветки `codex/backend` и `codex/frontend` после выбора архитектуры. Пока ветки не создавались.
- До разделения работы договориться о каталогах и владельцах общих конфигурационных файлов. Изменения общей схемы и API согласовывать сразу.
- Использовать один пакетный менеджер для каждого стека и сохранять его lock-файл в Git.
- В `.env.example` хранить только имена переменных и безопасные примеры. Реальные значения — в локальном `.env`.
- Первую интеграцию выполнить в первый час, затем соединять изменения небольшими порциями.
- Если фронтенд и бэкенд на разных машинах, `localhost` указывает на разные машины. Заранее проверить доступный адрес сервера, сеть и origin клиента. Способ соединения выбрать после определения платформы.

## Контракт API перед параллельной работой

Для каждой нужной операции заполнить:

| Поле | Содержание |
| --- | --- |
| Назначение | Какое действие пользователя обслуживает |
| Метод и путь | После выбора сценария |
| Запрос | JSON-пример или другой согласованный формат |
| Успешный ответ | Пример с типами и обязательными полями |
| Ошибки | Статусы, формат и сообщение для пользователя |
| Ожидание | Синхронный ответ или состояние длительной операции |

Также согласовать формат ID, даты с часовым поясом, различие отсутствующего значения и пустой коллекции. Фронтенд использует примеры из этого же контракта; демонстрационные данные явно обозначаются.

## Проверка платформы до начала основной разработки

- Веб: запускаются клиент и сервер; запрос проходит из браузера, а не только через curl.
- Десктоп: пустая оболочка выбранного стека собирается и запускается на машине демонстрации.
- Мобильное приложение: пустая сборка устанавливается на выбранное устройство или эмулятор и может обратиться к серверу.

Выбираем одну платформу по кейсу. Не тратим время на установку всех SDK заранее.

## Что должно появиться после выбора стека

- Зафиксированные версии среды, зависимости и команды запуска.
- Минимальный сквозной сценарий и проверка доступности сервера.
- `.env.example` с пояснениями.
- Одна команда или короткая последовательность запуска для каждого участника.
- Воспроизводимые демоданные и способ вернуть демо в исходное состояние.
- Проверка запуска с нуля на машине демонстрации.

Доступ к удаленному репозиторию, внешним API и SDK пока не проверен. Установок, публикаций и изменений внешних сервисов не выполнялось.
