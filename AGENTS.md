# Правила работы над хакатоном

## Подтвержденный контекст
- Команда: 2 человека, оба разрабатывают с помощью ИИ. Пользователь отвечает за бэкенд; фронтенд второго участника — рабочее допущение.
- Всего 4 часа: 3 часа разработки, последний час — тестирование, исправления и подготовка демонстрации.
- Выбран Flutter Web + FastAPI + SQLite. Основная платформа — веб по ТЗ; APK возможен позже и сейчас не реализуется.
- У участников разные ОС: Linux и Windows. Команды разработки должны учитывать обе ОС; не делать Bash, Unix-пути или Docker обязательными без необходимости.
- Получен кейс Career Quest, Halyk Bank / HackAlem AI: 1–3 объяснимых рекомендации, прогресс навыков и HR-срез. Геймификация необязательна.
- Команде важно неординарное, нестандартное решение. Новизна должна давать конкретное преимущество пользователю; необычный интерфейс или добавление ИИ сами по себе недостаточны.

## Разрешенный объем работ
Последнее указание пользователя разрешает **этап 2**: серверная авторизация демонстрационных сотрудников и HR, собственный профиль и история сотрудника, сохранение цели, HR-каталог сотрудников и JSON/CSV-импорт проверочных данных. Также разрешены обновление дизайна и логики интерфейса: убрать страницы технических срезов и сообщения о запуске FastAPI из пользовательского веба. Предыдущее ограничение этапом 1 заменено этим указанием.

Рекомендации, AI, выполнение активностей, расчётный прирост навыков и HR-аналитика остаются следующими этапами. Пользователь отдельно разрешил коммит и пуш проекта вместе с исходным синтетическим датасетом в существующий приватный репозиторий `BAITC-Hacks/hack-c6826b6b-peep`. Стартовые четыре JSON/CSV и три README из `data/sample/` включены в Git. Локальную SQLite с сессиями, секреты, произвольные импортируемые файлы, зависимости и сборки держать вне Git. Не менять видимость репозитория и не деплоить сайт без отдельного указания. Актуальный план: docs/05-roadmap.md.

## Правила этапа 2
- Авторизацию и права проверяет сервер. Сотрудник читает только собственный профиль и историю; HR имеет доступ к каталогу и импорту. Переключатель интерфейса не заменяет проверку доступа.
- Учётные записи демонстрационные и предназначены для локального запуска. Не представлять их как SSO или готовую банковскую систему доступа. Токен хранится в памяти Flutter; обновление страницы требует повторного входа.
- Импорт сначала проверяется без записи, затем подтверждается. Проверять формат, уникальность ID и связи всего итогового набора. Ошибка отклоняет весь пакет; повтор одинакового файла не создаёт дубликатов.
- По умолчанию отличающиеся записи с существующим ID отклоняются. Замена допустима только при явно выбранной политике. Устаревший или уже применённый предпросмотр не использовать повторно.
- SQLite хранит исходный набор отдельно от текущих импортированных записей и личной цели. Перезапуск не заменяет изменения исходным набором. Расчётный прирост не подменяет значения последней оценки.
- Если цель не задана, следующий грейд показывать как предложение. Он становится целью только после явного сохранения; для Lead не придумывать следующий грейд.

## Обязательное визуальное направление
Пользователь выбрал референс для всего сайта: `docs/design/style-reference.png`. Следующие страницы и компоненты должны сохранять этот стиль. Правила и палитра: `docs/08-design-system.md`; код общих компонентов: `frontend/lib/widgets/ui.dart`, тема: `frontend/lib/main.dart`.
- Тёмный navy-фон, сине-фиолетовые полупрозрачные карточки с тонкими контурами, мягкое свечение, розовые основные действия, бирюзовые и сиреневые акценты.
- Горная тропа как образ развития; декоративная иллюстрация отделена от интерактивного интерфейса и не заменяет реальные данные.
- Для новых экранов использовать существующую тему и компоненты. Сохранять читаемость, работу на узком экране, видимый фокус и понятные подписи состояния.
- Числа, аналитика, рекомендации и кнопки с референса не считаются реализованными функциями. Показывать только доступные сценарии и реальные данные.

## После получения кейса
1. Сформулировать пользователя, ситуацию, проблему и желаемый результат; отделить факты от предположений.
2. Предложить три направления: простое надежное, нестандартное реалистичное, смелое с сильным демо. Сравнить по критериям ниже, объясняя оценки; это инструмент обсуждения, а не прогноз баллов жюри.
3. До рекомендации кратко проверить данные, ключевую технологию и ближайшие альтернативы через доступный поиск. Не заявлять уникальность без проверки.
4. Для рекомендации определить один законченный сценарий MVP, наблюдаемый результат, способ проверки, самое рискованное предположение и условие упрощения или смены направления.
5. Объяснить выбор платформы через сценарий, возможности устройства и стоимость сборки/запуска в отведенное время. Не планировать несколько платформ одновременно без необходимости.
6. Задать максимум три существенных вопроса. Не готовить задание на реализацию в первом ответе по кейсу.
7. После выбора направления или «дальше» провести углубленное исследование и подготовить самостоятельный промпт для реализации, зафиксировав стек и допущения. Саму реализацию запускать только по отдельному указанию.

## Принципы будущей реализации
- Один основной пользователь и один сквозной сценарий для демо на 60–90 секунд.
- Согласовать контракт API до независимой работы над фронтендом и бэкендом; проверить их соединение в первый час.
- Самую опасную зависимость проверить в первые 15–20 минут. К концу первого часа стремиться получить работающий основной сценарий.
- Последний час не заполнять новыми функциями.
- Не имитировать работающие интеграции: деморежим и демонстрационные данные явно обозначать.
- Не выдумывать статистику, пользовательские исследования, измерения эффекта или результаты тестов.
- Масштабирование раскрывать через следующего пользователя/заказчика, условия внедрения и реальные препятствия.
